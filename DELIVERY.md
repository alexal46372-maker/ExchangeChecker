# DELIVERY.md — поставка Exchange Checker заказчику

Check ID: **CHK-DELIV-01**

## Принцип

Заказчик получает **только готовый zip с бинарниками**. Исходный код, инструкции по сборке и среда разработки заказчику **не передаются**. Сборка и упаковка выполняются **только в среде нейронки (AI)**; заказчик **никогда** не собирает продукт сам.

## Содержимое zip (план)

Типовая поставка — один архив, например `ExchangeChecker-<version>-windows-amd64.zip`, внутри:

| Файл | Назначение |
|------|------------|
| `ExchangeCheckerSetup.exe` | Инсталлятор (мастер установки). Внутри или рядом по схеме инсталлятора — служба и трей. |

Итоговые артефакты сборки (имена рабочих exe):

| Артефакт | Компонент |
|----------|-----------|
| `ExchangeCheckerSvc.exe` | Служба Windows |
| `ExchangeCheckerTray.exe` | Трей (UI) |
| `ExchangeCheckerSetup.exe` | Инсталлятор |

В zip для заказчика **не** включаются: исходники, `go.mod`/`go.sum`, тесты, `node_modules`, скрипты сборки, документация разработчика (кроме краткого README для пользователя при необходимости).

## Целевая платформа сборки

- ОС: **Windows amd64**, совместимость **NT 6.1+** (Windows 7 / Server 2008 R2 и новее)
- Компилятор: **Go 1.20.14**
- Флаги: `GOOS=windows` `GOARCH=amd64` `CGO_ENABLED=0`

## Рекомендации по внедрению: учётная запись SQL для мониторинга

Exchange Checker только читает базы 1С. Для мониторинга заведите **отдельный** логин (SQL-логин или учётную запись Windows/службы) и дайте ему в каждой контролируемой базе **только роль `db_datareader`**:

- не давать `db_owner`, `db_datawriter`, `db_ddladmin`, `sysadmin` и другие серверные роли;
- `VIEW SERVER STATE` и прочие серверные права не нужны (программа не использует `sys.dm_*`);
- не использовать логин `sa` и учётные записи 1С.

Пример (SQL Server 2008, выполняет администратор СУБД; имена — свои):

```sql
CREATE LOGIN [ec_monitor] WITH PASSWORD = N'<сложный пароль>', CHECK_POLICY = ON;
USE [base_1c];
CREATE USER [ec_monitor] FOR LOGIN [ec_monitor];
EXEC sp_addrolemember N'db_datareader', N'ec_monitor';
```

Это основная граница безопасности: даже если в профиль попадёт недопустимый ручной SQL, сервер не позволит изменить данные.

## Рекомендации по внедрению: шифрование подключения

По решению заказчика (сервер — SQL Server 2008 R2 RTM без SP) **основной режим — без шифрования**: новые профили и пресет «SQL Server 2008» создаются с `encrypt = disable`, профили из старого profiles.json без поля `encrypt` читаются так же (PLAN.md §12 п. 31).

- В этом режиме при SQL-аутентификации **пароль передаётся по сети практически открытым текстом** (маскировка TDS обратима), программа показывает предупреждение «пароль SQL передаётся без шифрования» (`sql.warn_plaintext_login`).
- Рекомендуется **Windows-аутентификация** (учётная запись службы или `DOMAIN\user`) — пароль по сети не передаётся, предупреждения нет. Если нужна SQL-аутентификация — только отдельный логин с `db_datareader` (см. выше), не `sa`.
- Если сеть не доверенная, включите в профиле шифрование: «только логин» (`optional`) или «полное» (`on`, при самоподписанном сертификате — «Доверять сертификату сервера»); пресет уже разрешает TLS 1.0 для серверов без обновлений TLS 1.2.
- Если на сервере включено «Force Encryption», режим «без шифрования» не подключится — выберите `optional` или `on`.

## Когда собирать

Сборка zip — **только по явной просьбе** заказчика (см. POLICY.md / PLAN.md §11 фаза 8).

## Проверка CHK-DELIV-01

Zip соответствует этому документу: есть установочный бинарник, нет исходников и лишних артефактов разработки.
